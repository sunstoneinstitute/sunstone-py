    Catalog-Aware datasets.yaml Design¶

    Date: 2026-04-14 Status: Proposed Related: #30 — Split datasets.yaml into human-authored and auto-generated files

    Problem¶

    datasets.yaml currently contains both human-authored declarations and auto-generated metadata (lineage, hashes). When input datasets come from the Sunstone data catalog (Iceberg + Nessie), maintaining field schemas, descriptions, and source attribution in datasets.yaml duplicates what the catalog already provides. This creates drift and unnecessary maintenance.

    Goals¶

    1. Catalog inputs should be minimal references in datasets.yaml — no duplicated metadata
    2. A lock file caches resolved metadata for offline work and reproducibility
    3. Git branch names sync with Nessie branches so PRs resolve automatically
    4. The plugin system declares metadata capabilities so the lock command knows what each source can provide
    5. Existing projects continue working with zero changes

    Design¶

    Approach: Lock File Does Everything¶

    A single datasets.lock.yaml serves as both the resolved metadata cache for inputs and the lineage store for outputs. This follows the DVC/Poetry/Terraform pattern of separating human intent from machine-resolved state.

    • datasets.yaml — human-authored declarations only
    • datasets.lock.yaml — everything resolved: cached fields/schemas, content hashes, snapshot IDs, output lineage, owner refs

    datasets.yaml — The Human-Authored File¶

    Catalog inputs¶

    Minimal — just a reference. Name, description, fields, and source attribution are resolved from the catalog at lock time.

    inputs:
  - slug: feed-consumption-raw
    location: sunstone://fishfarming/nutrient-analysis/feed-consumption-raw@${GIT_BRANCH:-main}

    The human can optionally add overrides (e.g. a project-specific description), which take precedence over catalog metadata.

    Local file inputs¶

    The handler can't provide rich metadata, so the human supplies it:

    inputs:
  - slug: manual-corrections
    name: Manual Corrections
    location: inputs/corrections.csv
    fields:
      - name: country
        type: string
      - name: correction_factor
        type: number
    source:
      name: Internal
      attributedTo: Sunstone Institute
      acquiredAt: 2026-03-15
      acquisitionMethod: manual
      license: CC-BY-4.0

    Outputs¶

    Declared with human-authored metadata. Lineage moves to the lock file:

    outputs:
  - slug: cleaned-feed-data
    name: Cleaned Feed Consumption Data
    location: outputs/cleaned_feed_data.csv
    fields:
      - name: country
        type: string
      - name: feed_tonnes
        type: number
        unit: t

    Top-level config¶

    package:
  title: Fish Farming Nutrient Analysis
  description: Analysis of feed consumption and nutrient loading

defaults:
  rdfPrefixes:
    gtio: https://sunstone.institute/rdf/gtio/0.2/

publish:
  - to: gs://bucket/datasets/fishfarming/nutrient-analysis/
    as: https://data.sunstone.institute/datasets/fishfarming/nutrient-analysis/
    datasets:
      - slug: cleaned-feed-data

    The publish key uses a list-of-packages format rather than the current per-dataset publish: field. Each package defines its destination and which datasets to include by slug. This supports publishing the same dataset in multiple packages.

    datasets.lock.yaml — The Resolved Snapshot¶

    Auto-generated by sunstone dataset lock, committed to git, marked linguist-generated=true in .gitattributes.

    Catalog input (resolved)¶

  - slug: feed-consumption-raw
    location: sunstone://fishfarming/nutrient-analysis/feed-consumption-raw@${GIT_BRANCH:-main}
    resolved_ref: main

    Local file input (resolved)¶

    Less metadata — the handler can only provide what it can detect:

      - slug: manual-corrections
    location: inputs/corrections.csv
    content_hash: sha256:b7c2e1f...
    row_count: 12
    fields:
      - name: country
        type: string
      - name: correction_factor
        type: number

    Fields are inferred from the file and merged with human declarations from datasets.yaml. Human-declared fields win on conflict.

    Output (lineage)¶

    outputs:
  - slug: cleaned-feed-data
    content_hash: sha256:e9f8d2a...
    created_at: '2026-04-10T14:23:01.508497'
    sources:
      - slug: feed-consumption-raw
      - slug: manual-corrections
    activity:
      id: urn:uuid:abc123
      started_at: '2026-04-10T14:22:58'
      ended_at: '2026-04-10T14:23:01'

      git_commit: 8af6c91

    field_derivations:
      - output_field: feed_tonnes
        source_entity: feed-consumption-raw
        source_field: feed_kg

    Resolution rules¶

    1. sunstone dataset lock iterates all inputs and outputs
    2. For each, asks the URL handler chain: "do you implement MetadataProvider?"
    3. If yes, calls resolve_metadata(url, capabilities) — handler returns what it can
    4. Merges: lock file = handler-resolved metadata + human overrides from datasets.yaml (human wins)
    5. For outputs, lineage is written by DatasetsManager.update_output_lineage() as it does today

    MetadataProvider Plugin Protocol¶

    URL handlers optionally implement MetadataProvider to declare what they can resolve.

    Capability flags¶

    class MetadataCapabilities(enum.Flag):
    FIELDS = auto()        # column names + types
    DESCRIPTIONS = auto()  # field/dataset descriptions
    VERSIONING = auto()    # branches, tags, snapshots
    CONTENT_HASH = auto()  # content checksum
    ROW_COUNT = auto()     # row count without full read
    PROVENANCE = auto()    # source attribution, lineage
    OWNER = auto()         # authoritative owner reference

    Protocol¶

    class MetadataProvider(Protocol):
    def metadata_capabilities(self, url: str) -> MetadataCapabilities:
        """Declare what this handler can resolve for the given URL."""
        ...

    def resolve_metadata(
        self, url: str, requested: MetadataCapabilities
    ) -> ResolvedMetadata:
        """Resolve metadata for the URL. Only populate requested capabilities."""
        ...

    ResolvedMetadata is a dataclass with optional fields matching each capability: fields, description, content_hash, snapshot_id, resolved_ref, row_count, source, owner. All optional; handlers populate what they can.

    Built-in handler capabilities¶

    Handler Capabilities
    LocalFileHandler FIELDS (infer column names), CONTENT_HASH (SHA256 of file)
    HttpURLHandler CONTENT_HASH (ETag if available)
    GcsURLHandler CONTENT_HASH (GCS object hash), ROW_COUNT (for Parquet)
    S3URLHandler CONTENT_HASH (S3 ETag)
    Catalog handler (in data-platform) All capabilities

    Field inference for local files is delegated to the FormatHandler — the URL handler opens the file and the format handler peeks at headers/schema.

    sunstone:// URI Scheme¶

    Format¶

    sunstone://{namespace-path}/{table}@{ref}
    • namespace-path: /-separated, maps to Nessie multi-level namespace. E.g. fishfarming/nutrient-analysis becomes ("fishfarming", "nutrient-analysis") in PyIceberg.
    • table: the dataset slug (last path segment before @)
    • ref: branch name, tag name, or ${GIT_BRANCH:-default}. Optional — omitting @ref implies @main.

    Examples:

    sunstone://fishfarming/nutrient-analysis/feed-consumption-raw@main
sunstone://fishfarming/nutrient-analysis/feed-consumption-raw@${GIT_BRANCH:-main}
sunstone://shared/countries-50m@v2.0
sunstone://energy-transition/eia-countries

    Git-Nessie branch sync¶

    ${GIT_BRANCH:-main} enables a workflow where:

    1. Data scientist creates git branch feature/new-analysis
    2. datasets.yaml uses @${GIT_BRANCH:-main} for catalog inputs
    3. sunstone dataset lock resolves to Nessie branch feature/new-analysis (if it exists) or falls back to main
    4. PR merges to main → lock resolves to Nessie main branch — no file changes needed

    If the git branch has no corresponding Nessie branch, the handler falls back to the default specified in :-. Not every git branch needs its own catalog branch.

    Variable substitution¶

    Only ${GIT_BRANCH} is supported, with default syntax ${GIT_BRANCH:-fallback}. Resolved by reading the current git branch. If not in a git repo and no default provided, error.

    Ref validation¶

    Ref validation is the catalog handler's responsibility, not sunstone-py's. The handler knows the backend constraints (Nessie naming rules: [A-Za-z-][A-Za-z0-9/._-]*[A-Za-z0-9_-], no .. sequences). sunstone-py only handles variable substitution.

    The catalog handler (lives in data-platform)¶

    The sunstone:// URL handler is a plugin in sunstone-data, registered via the sunstone.plugins entry point. sunstone-py never imports from sunstone-data. The plugin system handles discovery.

    Ownership¶

    Catalog tables have an owner — a pointer to the authoritative datasets.yaml that manages the dataset.

    owner:
  github: sunstoneinstitute/projects
  path: FishFarmingProject/nutrient_analysis/datasets.yaml

    The owner object supports github: (org/repo) initially, with git: (full remote URL) as a future extension.

    The catalog handler checks ownership on write: if a table already has an owner from a different project path, the write is rejected (on branches where the table already exists). The owner is stored in catalog table properties and cached in the lock file.

    sunstone dataset lock Command¶

    sunstone dataset lock [--offline] [--check]
    • Default: resolves all inputs and outputs, writes datasets.lock.yaml
    • --offline: skips network calls, only resolves local file inputs. Catalog inputs keep their existing lock entries unchanged.
    • --check: exits non-zero if the lock file is out of date (useful in CI, same pattern as uv lock --check)

    Lock file freshness¶

    --check compares the current lock against what a fresh resolve would produce. This lets CI enforce that the lock file was updated after datasets.yaml changes.

    Migration and Backward Compatibility¶

    Reading behavior¶

    DatasetsManager._load() uses this precedence:

    1. If datasets.lock.yaml exists → merge lock data into the in-memory model
    2. If no lock file but datasets.yaml has inline lineage: blocks → use those (today's behavior)
    3. If neither → datasets work but with no resolved metadata (first-time project)

    Existing projects continue working with zero changes.

    Migration command¶

    sunstone dataset migrate
    • Extracts inline lineage: blocks from datasets.yaml into datasets.lock.yaml
    • Removes lineage: from datasets.yaml
    • Moves per-dataset publish: into top-level publish: list format (if present)
    • Adds .gitattributes entry for datasets.lock.yaml linguist-generated=true (only if inside a git repo)
    • Reports what it did

    Writing behavior¶

    • DatasetsManager.update_output_lineage() writes to datasets.lock.yaml (not datasets.yaml)
    • DatasetsManager._save() writes only human-authored content to datasets.yaml
    • If no lock file exists yet, first write creates it

    Deprecation timeline¶

    1. v1.6: Lock file support added, migration command available, inline lineage still read (with deprecation warning)
    2. v1.7 (or later): Inline lineage triggers a warning recommending migration
    3. v2.0: Inline lineage no longer read

    Design Rationale and Prior Art¶

    Why a lock file (not inline metadata)¶

    Problem: datasets.yaml mixes human-authored declarations with auto-generated metadata. Code reviewers rubber-stamp diffs. Catalog inputs duplicate metadata that already lives in the catalog.

    Prior art: DVC (dvc.yaml + dvc.lock), Poetry/uv (pyproject.toml + lock file), Terraform (.tf + .tfstate). All separate intent from resolved state. dbt goes further with three tiers (human YAML, manifest, catalog).

    Decision: Single lock file containing all resolved/generated metadata. Marked linguist-generated=true for collapsed PR diffs.

    Why capability-based metadata¶

    Problem: Input sources vary wildly in what metadata they can provide. A CSV gives you column names (maybe). Iceberg+Nessie gives you everything.

    Prior art: dbt's three-tier enrichment (human fills what the warehouse can't), Frictionless Data's infer-then-enrich pattern, Dagster's observable source assets.

    Decision: MetadataCapabilities flags on URL handlers. The lock command asks "what can you tell me?" and caches whatever comes back. datasets.yaml carries whatever the handler can't provide.

    Why sunstone:// URI scheme¶

    Problem: Need a way to reference catalog datasets that fits the existing URL handler dispatch pattern.

    Prior art survey: LakeFS (lakefs://repo/branch/path) is the closest precedent — clean URI with version in path. Quilt uses quilt+s3://. No other data tool has a custom URI scheme for catalog references. None are IANA-registered. Iceberg, Unity Catalog, Hive, Delta Lake, dbt, DVC, and Frictionless Data all use dot-separated identifiers or plain paths rather than URI schemes.

    Decision: sunstone://namespace/table@ref. Uses our own namespace since this is our catalog. @ref follows Nessie's established convention. Ref validation is the handler's responsibility. The slash-separated namespace maps directly to Nessie's multi-level namespace model and enables path-based RBAC.

    Why ${GIT_BRANCH} substitution¶

    Problem: PRs should test against feature branches in the catalog. Merging to main should automatically resolve to the main catalog branch without file changes.

    Decision: Shell-style variable with default: ${GIT_BRANCH:-main}. Only this one variable. Resolved at lock time, concrete value stored in lock file.

    Why explicit sunstone dataset lock command¶

    Problem: When should metadata be refreshed from the catalog?

    Prior art: DVC requires explicit dvc repro. Poetry/uv require explicit lock. Auto-refresh on read (like npm's old behavior) caused surprise network calls and non-deterministic builds.

    Decision: Explicit command only. No network calls during pd.read_csv(). Offline work uses the lock file as cache.

    Why plugin-based catalog handler¶

    Problem: sunstone-py needs to resolve sunstone:// URIs but shouldn't depend on the data-platform package.

    Decision: The catalog handler lives in sunstone-data as a plugin registered via the sunstone.plugins entry point. sunstone-py defines the MetadataProvider protocol; the catalog handler implements it. This keeps sunstone-py decoupled and allows alternative catalog backends.

    Why output pre-registration is optional¶

    Problem: Should outputs be declared in datasets.yaml before they can be written?

    Prior art: DVC and Frictionless require pre-registration. dbt, Pachyderm, and Dagster auto-discover outputs.

    Decision: Use existing strict/relaxed mode. Strict mode requires declaration (production governance). Relaxed mode auto-registers on first write (exploration). No change needed.
